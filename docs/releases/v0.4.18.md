# miao v0.4.18

[简体中文](https://github.com/mttydev/miao/blob/main/docs/releases/v0.4.18.zh.md)

v0.4.18 makes it possible to find and resume a Session that was started in a
different directory. Before this, a Session ID alone did not say which file held
it, and the only way left was searching the disk.

## A Session ID now resolves across workspaces

Every workspace owns one engine database, named by the digest of its directory.
Keeping projects apart is the point, but it meant `miao -s ses_...` opened the
current directory's ledger, found nothing, and stopped. The mapping was never
lost — `engine_location` records which directory a Session belongs to, in the
ledger that owns it — it simply had no entry point.

`miao session find <id>` now reports the workspace and the ledger file that hold
a Session:

```
$ miao session find ses_18ea90403ed7491863740
ses_18ea90403ed7491863740
  workspace · /Users/…/20261123-溪口镇大厂地块
  ledger    · …/miao-engine/storage/f05d3f60….db
  continue  · miao -s ses_18ea90403ed7491863740
            (or run it from that workspace)
```

A unique prefix works too, and a prefix that matches several Sessions lists the
candidates rather than opening one at random. `--open` continues the Session
directly.

`miao -s <id>` now follows the ledger that owns the Session when the current
workspace's ledger does not know it, so a Session started elsewhere resumes
without re-spelling the workspace. An explicit `--db` still wins, because that
is a file the operator named themselves.

The lookup caches into `sessions-index.json` under the storage root. The cache is
an optimization only: a missing, corrupt or out-of-date index (a ledger added,
removed or changed since) falls back to scanning, and a ledger that cannot be
read is skipped rather than failing the lookup. On a machine with 511 ledgers and
2036 sessions, a cold lookup scans in 3.2 seconds and the cached path answers in
13 milliseconds.

**Nothing about where data lives changes.** There is no migration: an existing
installation gets this by upgrading, and the index builds itself the first time
you look something up.

## Two answers that used to mislead

`list_sessions` filtered to the current workspace and reported `no peer sessions`
— which reads as "your history is gone" when the Session simply lives in another
directory. It now says what it means, and points at `miao session find`.
`session_state` names that it reads only the calling Session.

`miao doctor` now reports an empty `~/.miao/miao.db`. That directory is the
install location, never a data directory, but an early build left a zero-byte
file there whose name and location read as the ledger — a detour for anyone
looking for their own history. The report explains where the data actually is.
