# miao v0.5.10

[English](https://github.com/mttydev/miao/blob/main/docs/releases/v0.5.10.md)

v0.5.10 是一个修复版本：账本繁忙不再中断正常运行的任务。

## 之前是什么在中断任务

回合以 `interrupted` 结束，没有报错也没有任何说明，位置正好在 assistant 这一步已提交、工具还没执行之间：「Tool 'bash' was not executed: the turn stopped before it ran.」

日志说明了它为什么像是"什么都没发生"：这些 run 完全没有 `run.cancel_requested` 事件，而同库每一次 Esc 取消都会记录 `reason=operator`。收尾写入仍然通过了租约栅栏，说明也没有别的窗口接管该会话。于是只剩一条路径——租约续期。一个 drain 每两秒续一次会话租约，而这次续期的任何错误都会取消整个回合，既不记来源，也不写日志。

## 续期为什么会失败

续期是对共享账本的一条裸 `UPDATE`，最多只等存储的 5 秒 busy 窗口。在几个窗口同时写入的多 GB 账本上，只要有一个写事务持锁超过 5 秒，续期就会以 `database is locked` 失败——回合随之死掉。

在被卡住的那个窗口上抓栈，可以看到卡顿的两半：

- `WriteTx::commit` 在每次提交后都执行 `PRAGMA wal_checkpoint(PASSIVE)`。checkpoint 需要持有 WAL 写锁，而这正是其他写者与每次续期都要抢的锁；它还发生在提交仍持有跨进程写锁的时候，并且为此每次提交都新建、销毁一条临时连接。
- 续期排在共享 store worker 的队列里，而这条队列同时还在跑 `git` 探针和整段投影。

在本次诊断用的账本上，获取写锁的等待常态是 0.5–1.6 秒，其中一次超过 5 秒。

## 改了什么

- 只有当存储明确回答"租约被接管"（fenced）时，续期失败才视为失去所有权：此时停轮并记录 `lease_lost`。其他错误都视为卡顿——重试、记 `lease renewal failed`，回合继续。
- 续期拥有自己的连接和阻塞线程，窗口为两个租约周期：既能等过别的窗口的写事务，也不会排在 `git` 调用后面。
- `WriteTx::commit` 不再做 checkpoint。运行时在 WAL 超过 8 MiB 时用定时任务合并，普通提交的代价就是一次提交。
- 写者的 busy 窗口提升到 20 秒：维护性操作会让普通写入等待，而不是失败。
- TUI 会把两种引擎决定的停止说清楚（「另一个窗口接管了该会话」「会话租约无法续期」），不再显示 `stopped (lease_lost)`。
- 写事务持锁达到 1 秒以上时会记录账本与耗时，下一次卡顿能自己报出名字。

## 验证

- `crates/miao-engine` 的 `cargo test --lib`：649 项通过。
- `crates/miao-engine` 集成测试 `store`、`session_fence`、`concurrent_open`、`http_leases`、`snapshots`、`revert`、`run_admission`、`renewal`：全部通过。
- `renewal` 中有一条回归测试：外部持有写锁 6 秒，续期仍必须成功；旧实现在 5 秒窗口处就会失败。
- `crates/miao-tui` 的 `cargo test --lib`：中断行会写明两个新来源。

## 升级建议

如果你遇到过长时间运行的任务自己停下、提示 "nothing is running now"，请升级。升级后请重启所有窗口：仍在运行旧版本的窗口会在每次提交时继续做 checkpoint，而正是它造成本版移除的卡顿。
