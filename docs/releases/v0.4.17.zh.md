# miao v0.4.17

v0.4.17 让来自 Windows 主机的命令输出变得可读。Windows 控制台程序打印的中文，此前到引擎这边是一串替换字符，因为引擎把这些字节当成 UTF-8 来解码。

## GBK 输出改为正确解码，不再被抹平

只要控制台代码页是中日韩默认值，Windows 控制台程序就写 CP936；`cmd` 和 PowerShell 经 SSH 连接时同样保持这个代码页，系统区域不是中文也不会改变它。引擎过去用 `from_utf8_lossy` 读取所有命令输出，每一对中文字节都变成 U+FFFD：

```
$ ssh build-host 'reg query "HKLM\SOFTWARE\OpenSSH" /v Nope'
����: ϵͳ�Ҳ���ָ����ע������ֵ��
```

这些字节一直是那条消息 `错误: 系统找不到指定的注册表项或值。`，错的只是解码方式，文字本身完全可以找回来，并没有丢。

现在的输出按三步解码：

- 合法的 UTF-8 原样返回，本来就输出 UTF-8 的命令行为完全不变。
- 否则按 GB18030（GBK 的严格超集）严格解码，并容忍末尾不完整的序列，32 KiB 截断或一次读取的边界都不会污染缓冲区。
- 不像文本的内容保留原先的有损行为。

二进制的判据在这里很关键。严格 GB18030 解码本身已是强证据，但短小的偶然解码确实存在，而 PNG 文件头恰好是个陷阱：`89 50 4e 47` 开头是一对合法 GBK 字节，解出一个汉字，因此「含一个汉字」的规则会把文件头当成文本。现在要求文本中至少有两个不同的中日韩字符。随机缓冲区实测误判率：64 字节 0.005%，256 字节、2 KiB、8 KiB 均为 0%；PNG、gzip、zip 文件头在 16 字节、64 字节、2 KiB 下都保持二进制。

同一个解码器也用于后台任务运行中上报的实时输出，以及终端读取路径。一次管道读取可能停在多字节字符中间，因此读取方只上报完整的前缀，把残缺的尾部留到下一块，不会在分块边界冒出替换字符。

CP936 里那些非中日韩的字符——`℃`、`α`、`№`、制表符——只要中日韩文本锚定了缓冲区，就属于正常的消息内容，会原样通过。

## 本次其他改动
