# miao v0.3.90

[简体中文](https://github.com/mttydev/miao/blob/main/docs/releases/v0.3.90.zh.md)

v0.3.90 makes a picked model take effect, gives a spent Goal budget a way forward, keeps a trimmed request trimmed, and has the sidebar say whether a Goal is working or waiting.

## A picked model owns the account it needs

`/models` picked a model, and the Session kept the account `/accounts` had pinned earlier. The engine dropped the account a picked route belongs to whenever that account was the provider's default, then resolved the pick through the old pin; a pick from another family came back as a model the old account serves, so the picker looked like it had kept the old account and ignored the choice.

A pick now keeps the pin only while that pin still serves the picked model, compared on the model family so two accounts of one provider stay apart. Otherwise the pick owns the account: it moves the pin to the account the picked route belongs to, or clears it when the picked model lives on no account route. A variant or picker update that addresses a route the pinned account still serves never clears the pin.

## A spent Goal budget is the operator's to lift

A Goal's budget stops the drain at the boundary *before* the next provider turn, and a Goal is written only by the `goal` tool — which runs inside exactly that turn. Once the turn budget was spent, every message started a run that ended with no provider step: no reply, no error, and no way to follow the stop note's own advice ("raise the budget and send a message"). `/goal budget <turns>` now writes a new Goal revision with only the turn bound replaced, keeping the objective, status, evidence and every other budget axis, and the Session resumes with the inputs already waiting in its durable inbox.

## A trimmed request stays trimmed

A Session that switched to a smaller-window model had one request trimmed and answered, then the next step rebuilt the same 9 MB history while the engine compared the provider's count of the *trimmed* request with the window — so the whole history went out and was refused with `Prompt exceeds max length`, on every retry. The bound a trim imposes now lasts for the rest of the drain, a settled compaction clears it, and a trim also asks for the compaction pass that shrinks the durable history instead of re-trimming it every step. The length refusal is recognised as a context overflow, so a first request that is already too large recovers by compacting rather than being retried.

## A Goal says whether it is working or waiting

The sidebar printed `GOAL · active` for every unfinished Goal, which reads the same whether the Session is moving or stuck on something only the outside can move. It now names the state: `blocked · external` (the engine already refuses a blocked Goal that names nothing outside the Session), `working · decomposing` while runnable checklist items remain, and `waiting · external` once every open item is `waiting` or `blocked`.
