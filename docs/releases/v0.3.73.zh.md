# miao v0.3.73

[English](https://github.com/mttydev/miao/blob/main/docs/releases/v0.3.73.md)

v0.3.73 让 `/clear` 名副其实，让自动压缩在请求真正能达到的位置触发，并把底部条从侧栏里挪了回来。

## `/clear` 在所有客户端都真正生效 (#3035, #3036)

引擎从不删除任何东西：`/clear` 用一个空摘要的检查点让下一次 provider 前缀从空白开始，历史行全部留作审计。两个客户端都忽略了这个检查点。TUI 清空面板后，下一次重新投影（传输重同步、静默帧恢复）又从快照重建了整段对话，于是被清除的轮次过一会儿又回来了；侧栏的 context 行仍在显示刚被丢弃那段对话的占用；桌面窗口把事件流从序号零开始附着，重开一个已清除的会话就把全部内容重放一遍，表头还继续数着消息条数。

现在 TUI 的投影从 clear 检查点之后开始，并把 transcript 的尾部序号设在切点处，切点之前记录过的失败不会再挂在空面板后面；`usage_report` 在 clear 晚于最后一轮时报告零占用，`ContextCleared` 会重新取一次；桌面端从快照读出切点并在其后附着，只统计切点之后存活的消息，并保持会话界面而不是退回首次使用欢迎屏。

## 自动压缩在请求真正能达到的位置触发 (#3034, #3038)

一个会话停在 654K tokens、阈值却是 922K，而同一段对话在界面上是按 655K 的上限算的。两个数字对各自的输入都是对的：一次请求只能发送「模型窗口减去必须预留的输出」（deepseek 路由声明了 393,216），而未声明的容量被读成了「不预留」。`input_ceiling()` 现在在一处解析这个预留——声明的容量照用，未声明的按窗口四分之一兜底，任何声明都不得占用超过一半——触发点与界面百分比因此读同一个数字。

但仅仅能触发还不够，摘要跑不完等于没修：每次摘要调用都是固定 20 秒超时，而一次调用可能携带几十万 token，于是超时、记为 `summary timeout`、被 gate ⑤ 计数，三次之后会话被告知「自动压缩已暂停」——恰恰是最需要压缩的场景。现在预算随调用要读的文本伸缩：每 5000 字符加 1 秒，下限 20 秒、上限五分钟，prefix 尝试、每个分段以及溢出截断后的重试共用这套预算。`Budget::threshold` 还保证小窗口下触发点可达；拿不到窗口的会话会一次性说明原因并记录 `compaction.disabled`（原因、模型、修法），不再静默失效。

## Windows 上的 shell 动作改为询问而不是自行放行 (#3037)

`product_permission` 用 Unix shell 语义解析命令来判断 shell 动作：`git status` 解析出来是安全的，但 Windows 上真正执行的那条命令行（cmd 或 PowerShell 的引号、内建命令、驱动器相对路径）并不是被解析的那一条，于是策略期待「询问」的只读 bash 动作被放行了。现在 bash 分支只在 unix 编译；Windows 上 shell 动作一律询问。edit 分支不变——它是路径判断，受保护的 `.env` 编辑本来就会询问。

## Windows 的名称与路径统一拼法 (#3030, #3031, #3033)

三处 Windows 专有的不匹配，成因都是「verbatim 前缀（`//?/C:/…`）撞上普通路径」：

- `@reference` 名称带了前缀，写成 `@reference/**` 的策略会撞到 `?` 段而永不匹配——被拒绝的指令文件仍进入系统上下文，逐文件的 skill 策略被忽略。#3033 让名称始终带分隔符，#3030 在命名资源时剥掉前缀。
- 产品权限分类器用 `strip_prefix` 拿原始拼法比较请求资源与宿主目录，明明在工作区内也被判成区外——auto 模式下这让一次受保护的 `.env` 编辑变成了自动放行。两侧现在都走工具层的 `canonical_plain`（#3031）。
- formatter 夹具用 `cmd /d /s /c` 加带引号的重定向目标；`/s` 会重新解析该命令行，写入落到别处、formatter 报 `failed`。改为用 PowerShell 与字面路径写入（#3030）。

## monitor 的完成通知不再被拒 (#3028)

已结束任务的 steer 通知固定用 `monitor:<job>:finished` 作为 id，而它的正文在多次投递之间会变（notice 变为 some、状态快照变化）。复用 id 只有在所有字段都一致时才算精确重试，于是第二次投递抛出 `input id conflicts with an existing admission`，被记为 `monitor.notice_failed`。现在完成投递也像上面的逐条通知一样追加 uuid，重复投递是第二条消息而不是被拒绝。

## TUI 细节 (#3032, #3039, #3040)

- 侧栏与 `/context` 各自用自己的窗口去除占用；按输入上限计算时，同一段对话在一处显示 52%、另一处超过 100%。现在由同一个 helper 回答两处并把结果封顶在 100：溢出的上限读作满，而不是 131%。粘贴的截图也不再共用一个文件名，而是按标记命名（`image-1.png`、`image-2.jpg`）（#3032）。
- 事件队列满时到达的剪贴板结果会被合并丢弃——而那个事件正是清除「剪贴板读取中」标记的那一个，于是本轮之后 Ctrl+V、Alt+V 与 `/paste` 全部静默失效。现在剪贴板结果不受队列压力影响，必定送达（#3039）。
- 队列行、输入框与状态行按整帧宽度布局，而只有 body 被分栏，于是长队列文本和状态行右端的版本号跑到了侧栏下面。三者现在都止于正文列的分隔线，整条带的底色仍铺满整行（#3040）。
