# miao v0.4.18

v0.4.18 让「在别的目录里开始的会话」可以被找到并继续。此前只给一个会话 ID 并不知道它存在哪个文件里，唯一的办法是全盘搜索。

## 会话 ID 现在可以跨工作区定位

每个工作区各自拥有一个引擎数据库，文件名由该目录的摘要决定。把不同项目分开本身就是目的，但代价是 `miao -s ses_...` 只打开当前目录的库，找不到就停住。这层映射其实一直存在——拥有该会话的库里，`engine_location` 记着它属于哪个目录——只是没有入口去查。

`miao session find <id>` 现在会报出该会话所属的工作区和库文件：

```
$ miao session find ses_18ea90403ed7491863740
ses_18ea90403ed7491863740
  workspace · /Users/…/20261123-溪口镇大厂地块
  ledger    · …/miao-engine/storage/f05d3f60….db
  continue  · miao -s ses_18ea90403ed7491863740
            (or run it from that workspace)
```

唯一前缀同样可用；前缀命中多个会话时会列出候选，而不是随便打开一个。加 `--open` 可直接继续该会话。

当当前工作区的库不认识某个会话 ID 时，`miao -s <id>` 现在会跟随真正拥有它的库，因此别处开始的会话不必再重述工作区就能续跑。显式给出的 `--db` 仍然优先，因为那是操作者自己点名的文件。

查找结果缓存在存储根目录下的 `sessions-index.json`。缓存只是优化：索引缺失、损坏或过期（库被新增、删除或修改）时都会退化为扫描；某个库读不出来时跳过它，而不是让整次查找失败。在一台有 511 个库、2036 个会话的机器上，冷查找全扫耗时 3.2 秒，走缓存为 13 毫秒。

**数据存放位置没有任何变化。** 不需要迁移：已有安装升级即生效，索引会在第一次查找时自行建立。

## 两处会误导的答复

`list_sessions` 只列当前工作区，之前返回 `no peer sessions`——当会话只是存在别的目录时，这句话读起来像是「历史没了」。现在它如实说明含义，并指向 `miao session find`。`session_state` 也标明自己只读当前会话。

`miao doctor` 现在会报出空的 `~/.miao/miao.db`。那个目录是安装位置，从来不是数据目录，但早期版本在那里留下过一个零字节文件，名字和位置都像那个库——寻找自己历史的人会因此绕远路。报告会说明数据实际在哪里。

## 网关静默现在会重放，而不是直接结束该轮

某轮可能报 `provider sent no response bytes` 失败，下一次提问在同一条历史上以同样方式失败。静默是真的，但归类错了：引擎问的是「有没有收到帧」，而不是「有没有收到内容」，于是一个先吐出 assistant 角色或 usage 块、随后静默的网关被归为流错误——那是个无法重放的终止分支。现在改读引擎自己对「已发布内容」的定义，同样的静默归为传输失败并重试。
