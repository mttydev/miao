# miao v0.3.92

[English](https://github.com/oxdingzg/miao/blob/main/docs/releases/v0.3.92.md)

v0.3.92 让恢复后的会话看起来仍是你离开时的那一个，让长时间的实现不再被 stale-list 误停，并让一次卡住的 CI 作业不再挡住发布。

## 长时间实现不再被当成陈旧的清单

待办陈旧守卫在持久清单连续 12 个 provider 回合没有变化时停下 drain。12 这个值取自一条漂移了 176 回合的会话，但它也会停下一直在干活的会话：一条在收尾发布，另一条在十几次工具调用里实现同一个 `in_progress` 条目。两者都白费一次操作者消息才继续，而工作本身从未脱节。

上限现在改为 24。它仍然能报告守卫要防的那种失败——同样的漂移会在第 24 回合停下，而不是 176——但一段较长的实现不再被读成陈旧清单。三回合后的温和提醒与八回合后的明确指令保持不变。

## 恢复会话不再是满屏的暂停块

过去每条 `loop.stopped` 都会在记录里画一块「⋯ context · engine」，而用 `miao -s` 恢复会话时会回放这个会话记录过的所有暂停。一条在等后台任务时每个回合都暂停一次的会话，回来时就成了整列一模一样的 `paused: waiting` 方块——0.3.91 里有一条会话攒了 51 块——真正的对话被压在下面。

暂停是状态事实，不是消息：引擎早已把完整说明作为 injected context 持久保存，操作者仍能读到。现在视图只保留最新的一块暂停记录，恢复后的样子与离开时一致。

## 会自我恢复的发布链路

同一次发布撞上两次基础设施故障，都得人工取消再重跑。自动重试现在检查 run 里的每个 job，而不是只看整轮结论：于是「其余 job 仍在跑、单个 job 被平台取消」也会被处理，卡死到自身作业时限才被杀的 self-hosted 作业同样如此；真正的失败仍然保持红色。

发布门禁也等得起这套恢复动作：等待上限改为 150 分钟，足够一个作业跑到 60 分钟时限、再让重试跑完，而不会在第 45 分钟就驳回一个代码全绿的提交。有一条测试从 CI 计划里推导这个预算，将来新增更长的作业也不会悄悄超出。

## Windows 上不再因负载让取消权限 fixture 失败

Windows 发布门禁上，两个取消测试在 579 个其它测试并跑时 5 秒超时，重跑即过。那个等待是 fixture 的启动预算，不是边界断言，现在放宽到 60 秒；用于衡量取消多快落地的测试仍保留各自的短期限。
