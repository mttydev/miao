# miao v0.3.90

[English](https://github.com/mttydev/miao/blob/main/docs/releases/v0.3.90.md)

v0.3.90 让选中的模型真正生效，给用尽预算的目标一条出路，让被裁剪的请求保持裁剪，并让侧栏说清目标是在做还是在等。

## 选中的模型会带走它需要的账号

在 `/models` 里选了模型，会话却继续沿用之前 `/accounts` 钉住的账号。原因是：只要选中路由所属的账号是 provider 的默认账号，引擎就会把它丢掉，再用旧 pin 去解析这次选择；于是换个模型家族的挑选被换回成旧账号能服务的模型——看起来就像「换了模型却留着旧账号」，实际连模型都没换过去。

现在只有旧 pin 仍能服务所选模型时才保留它（按模型家族比较，避免把同一 provider 的两个账号混为一谈）。否则这次挑选接管账号：把 pin 迁到所选路由所属的账号；所选模型不属于任何账号路由时则清除 pin。指向「pin 仍服务的那条路由」的变体更新或选模更新，永远不会清掉 pin。

## 用尽的目标预算由操作者来放宽

目标的预算会在**下一个 provider 回合之前**的边界上中止 drain，而目标只能由 `goal` 工具写入——这个工具恰好需要那个回合。于是回合预算一旦用尽，每条消息都会开出一个连一个 provider 步骤都没有的 run：没有回复、没有报错，也无法照停止提示说的「提高预算再发一条」去做。现在 `/goal budget <turns>` 会写入新的目标 revision，只替换回合上限，保留目标、状态、证据与其它预算轴，并唤醒会话，让 inbox 里已经等待的输入继续。

## 被裁剪的请求会保持裁剪

切换到窗口更小的模型后，会话有一次请求被裁剪后得到了回复；下一步却重新从持久历史组装出同样 9MB 的内容，而引擎拿「provider 对**被裁剪请求**的计数」去和窗口比较，于是整份历史被发了出去，每次重试都被 `Prompt exceeds max length` 拒绝。现在一次裁剪施加的 bound 会在本次 drain 的后续步骤继续生效，压缩落地后清除；裁剪同时会登记一次压缩，让持久历史真正缩小，而不是每步重复裁剪。长度拒绝也会被识别为上下文溢出，因此「第一条请求就已经过大」的情况会通过压缩恢复，而不是被当作普通失败重试。

## 目标会说清它在做还是在等

此前每个未完成的目标都显示 `GOAL · active`，看不出会话是在推进，还是卡在只有外部能推动的事情上。现在会写明状态：`blocked · external`（引擎本来就拒绝不带外部依赖证据的 blocked 目标）、还有可运行的清单项时显示 `working · decomposing`、所有未完成项都是 `waiting` 或 `blocked` 时显示 `waiting · external`。
